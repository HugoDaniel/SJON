# SJON for LLMs: a machine-verified pack

This directory packages SJON for a model to consume: a paste-into-context
primer, a set of worked **write → validate → repair** flows, and a
token-efficiency receipt versus JSON + JSON Schema. It targets small, fast
models driving *dynamic spec* flows (generate a document, validate it, read
the structured diagnostic, repair, repeat) where SJON's stable diagnostic
codes turn every error into an instruction and its density keeps the loop
cheap.

Nothing here is hand-waved. Every diagnostic transcript is literal CLI
stdout, re-run and byte-compared by a build gate, so the examples cannot rot.

## What's here

| Path | What it is |
| --- | --- |
| `PRIMER.md` | The artifact to paste into a model's context. Budget-capped (≤ 10,000 chars). Its diagnostics table is generated from the CLI, so it stays truthful. |
| `flows/NN-*/` | Eleven worked repair loops. Each has a `task.md` (the task as given to a model, plus an `expects:` code the gate asserts), the `.sjon` attempts, and a `*.diagnostics.json` golden per attempt, the exact bytes `sjon validate … --format=json` emits. Flow 10 also ships a `sjon-project.sjon` + `manifests/`, because its schema declares a provider and a provider names compiled code. |
| `token-comparison/` | The same contract expressed as SJON and as JSON + JSON Schema, with a generated `TOKENS.md` counting both sides. The JSON Schema is generated by SJON's own exporter (a bias in JSON's favor), and hand-written artifacts are labeled as such. |

## The loop these flows teach

```
1. Write a .sjon document (schema is usually inline, as a (plugin …) manifest).
2. sjon validate FILE --format=json --no-project
   (a project on disk instead: drop --no-project, or --project-root=DIR)
3. If "diagnostics" is [] and exit is 0, you are done.
   Else take the FIRST diagnostic's `code` and `path` and repair by them.
   The `message` prose is human-facing and NOT wire-stable; match on `code`.
4. Optionally `sjon explain <code> --format=json` for the code's meaning.
5. Go to 2.
```

The flows cover the errors a model hits most: `unknown_key`,
`missing_required_key`, `duplicate_key`, `wrong_underlying`, `not_member`,
a discriminated-form pair (`missing_discriminant_key` → `unknown_key`),
`not_cross_ref`, and `arity_mismatch` inside an expression. Flow 09 is the
all-clean *grow-and-validate* cadence itself. Flow 10 is `not_cross_ref`
again, on a cross-ref whose legal names are extracted from a string inside
the document: the same code, a different repair, and the one place a model
is most likely to loop by "fixing" the reference site over and over. Flow
11 is `not_cross_ref` a third time, and the other place a model loops: the
declaration is spelled right and sits inside an **opaque slot**
(`:walk-opaque true`), where nothing registers a name. The repair is to
move the declaration, not to touch the reference.

## Verify / regenerate

```
zig build llm-pack-verify              # re-run every flow, byte-diff goldens, check the primer budget
zig build llm-pack-verify -- --replay  # print each flow's task → attempt → diagnostic → fix transcript
zig build llm-pack-verify -- --regen   # overwrite goldens + generated sections after an intended change
```

The verifier drives the real `sjon` binary (`zig-out/bin/sjon`, or `$SJON_CLI`),
so a green run *is* the end-to-end proof that these loops behave exactly as
written. A wording change in a diagnostic message trips the gate; `--regen`
refreshes the goldens and the commit diff shows the change, the same contract
the `export-schema-demo` goldens use.
